# lab04
1. Таблиця PID/PPID для кількох екземплярів process_info
Instance 1: PID = 4217, PPID = 3950
Instance 2: PID = 4218, PPID = 3950
Instance 3: PID = 4219, PPID = 3950
Один executable файл при кожному запуску створює окремий process зі своїм PID. Program — це статичний файл на диску, а process — запущений екземпляр програми в операційній системі зі своїм станом, адресами та ресурсами.

2. Короткий аналіз /proc/PID
Через /proc/PID можна переглянути cmdline, status (Name, State, Pid, PPid), exe (посилання на executable) та maps (відображення пам'яті). Каталог /proc/PID не є самим process, а лише способом спостерігати його стан з боку ядра; після завершення process він зникає (крім випадку zombie до збору статусу).

3. Приклад write() зі strace та пояснення
write(1, "Hello from process!\n", 20) = 20
write() — системний виклик (перехід у kernel mode для запису байтів у дескриптор 1 / stdout). printf() — функція стандартної бібліотеки C, яка використовує буферизацію і не завжди викликає write() на кожен виклик printf().

4. Результат експерименту fork()
До fork() існує 1 process, після успішного fork() — 2 processes (parent та child). Порядок виводу повідомлень від parent і child визначається планувальником ОС і не гарантується.

5. Пояснення значень повернення parent / child
Після рядка pid_t pid = fork(); виконання продовжується в обох processes: у child функція fork() повертає 0, а у parent — PID створеного child process (або від'ємне значення при помилці).

6. Результат fork_memory.c
Parent і child мають незалежні адресні простори. Зміна value = 300 у parent не змінює value = 200 у child. Однакова віртуальна адреса &value в обох processes не означає спільну змінювану пам'ять, бо кожен process має власну трансляцію віртуальних адрес.

7. Пояснення wait() та exit status
wait() і waitpid() змушують parent чекати завершення child та збирати його статус. У wait_basic.c значення 42 — це exit status (код завершення), а не PID. Макрос WIFEXITED(status) перевіряє нормальне завершення, а WEXITSTATUS(status) повертає код 42.

8. Результат експерименту exec()
Успішний виклик exec() (наприклад, execlp) замінює образ поточної програми в process на нову програму. Новий process не створюється, PID залишається тим самим, а код після успішного exec не виконується.

9. Схема fork -> exec -> wait
Parent -> fork() -> створює Child.
Child -> exec() -> замінює образ програми на іншу (PID той самий) -> завершується.
Parent -> wait()/waitpid() -> чекає завершення Child, отримує exit status -> продовжує роботу.

10. Результат експерименту zombie
Якщо child завершився, а parent ще не викликав wait(), child стає zombie (стан Z): інструкцій не виконує і CPU для роботи програми не використовує, але запис про нього залишається в системі, доки parent не викличе wait() або не завершиться. Після додавання wait(NULL) parent чекає child і забирає його статус.

11. Process tree для двох fork()
При двох послідовних fork() з'являється 2^2 = 4 processes (printf виконається 4 рази):
P0 (початковий)
 |-- fork1 -> P1
      |-- fork2 -> P3
 P0 -- fork2 -> P2

12. Короткий аналіз process_runner
process_runner виводить PID parent, робить fork(), у child показує PID та PPID і через execvp запускає передану program, а у parent чекає через waitpid(), перевіряє спосіб завершення, виводить exit status і продовжує роботу.
Типові фрагменти strace -f -e trace=process ./process_runner date:
- Створення process: clone(...) або clone3(...) = <child_pid>
- Запуск нового program image: execve("/usr/bin/date", ["date"], ...) = 0
- Очікування/завершення child: wait4(<child_pid>, ..., 0, ...) та exit_group(0)

13. Відповіді на контрольні питання
1. Program — файл на диску, process — запущений екземпляр програми в пам'яті зі своїм станом і ресурсами.
2. PID — унікальний ідентифікатор process.
3. PPID — ідентифікатор батьківського process (parent PID).
4. Кожен запуск створює окремий process з власним PID.
5. /proc/PID показує стан та параметри process через інтерфейс ядра.
6. System call — звернення програми до ядра ОС для виконання системної операції.
7. Звичайна функція виконується в user space, а system call переводить виконання в kernel space.
8. strace відстежує системні виклики та сигнали process.
9. fork() створює новий child process.
10. Після одного успішного fork() існує 2 processes.
11. У child fork() повертає 0, щоб відокремити гілку child від parent.
12. Parent отримує PID створеного child process (або -1 при помилці).
13. Ні, після fork() у них окремі копії змінної у різних адресних просторах.
14. Бо це віртуальні адреси, які в різних processes відображаються на різні ділянки пам'яті.
15. exec() замінює поточну програму в process на нову.
16. Ні, новий process exec() не створює.
17. Після успішного exec() PID не змінюється.
18. wait() потрібен для очікування завершення child і отримання його exit status.
19. Exit status — код, з яким завершився process (0 зазвичай означає успіх).
20. Zombie process — завершений process, чий exit status ще не забрав parent через wait().
21. Ні, zombie вже завершений і не виконує інструкцій.
22. Ready чекає на CPU, Running виконується на CPU, Waiting очікує подію (таймер, I/O тощо).
23. Порядок визначає планувальник ОС, а не код програми.
24. Shell робить fork(), у child запускає команду через exec() і викликає wait() для очікування завершення.

14. Висновок
У лабораторній роботі досліджено поняття process та system calls, роботу fork(), exec() і wait(), незалежність адресних просторів, стани process та виникнення zombie process.
